# Model tiers, review agents and an orchestrator: what I measured

*I pinned a model to each Claude Code agent, built an orchestrator to decide when to delegate and review, then benchmarked all of it; the cheap parts held up, the expensive part didn't, and the way I kept getting my own measurements wrong taught me more than the results did*

Start here: set a model and an effort level in each agent's frontmatter, write the rules your team's reviewers keep repeating into CLAUDE.md yourself, and leave the orchestrator off until you've tested it on your own work. On the model I started with it cost about three and a half times as much as plain Sonnet on the library back-office task, more on the big jobs, and it never beat plain Sonnet by more than the noise. On the newer model, on three-ticket jobs, it mostly did the work itself and scored like plain Sonnet. When I counted the review comments a pull request would draw, a rules file I wrote cut them from about eight a job to about three for about 12 per cent more money, and nearly all of that came from one rule, check every caller in all the repos, since take it out and the count goes back to 7. A fresh agent that wrote its own rules from my list of complaints, without seeing the repos, produced a caller rule too and got a 16 per cent cut, with the consumers left broken in every run, because nothing in it said where the other repos were, although in a second scenario in a different domain the same wording cut the count by 28 per cent, so how much a general rule gives is less settled than I first wrote. My own rules file cut the second scenario by 62 per cent as well. A checklist and the orchestrator did nothing, and a reviewer pass did nothing until it was told where the other repos were. I then tried the orchestrator on a 216-file front-end job, where it cost about 1.2 times plain Sonnet for the same result, ran the clinic chain out to five tickets, where only the reviewer stopped the agent breaking its own earlier work, and ported it to Go and Python, where both the rules file and the reviewer cut the count by more than half again.

One thing before the numbers. Everything below was measured on one version of Sonnet, and on the last day of testing Claude Code updated itself in the middle of a batch and the name "sonnet" started pointing at a newer model. The helpdesk task that cost me $2.50 and eleven minutes on the old one cost 44 cents and about two minutes on the new one, and scored higher, so read the old numbers as a record of what each method did to that model, and read the section on the model change for what held up on the current one.

Most of what you hand an AI model is boring shit, renaming a variable, reflowing a markdown file, tidying a config, and it all gets the same expensive model as the genuinely hard work because nobody told it otherwise. I wanted the cheap jobs on a cheap model, the hard jobs on the strongest one, and some way to tell whether any of it was working.

## Tiers live in the agent file, not in the proxy

Each subagent states its own model and effort, so the right tier applies without you thinking about it.

| Job | Model | Effort |
| --- | --- | --- |
| Formatting, tidy-ups | Haiku | low |
| Quick review of a small change | Sonnet | low |
| Writing tests, standard features | Sonnet | medium |
| Subtle logic, concurrency, security | Opus | high |

```yaml
---
name: code-reviewer
model: sonnet
effort: low
tools: Read, Grep, Glob
---
```

If `CLAUDE_CODE_EFFORT_LEVEL` is set anywhere it overrides all of this, so check you haven't.

I started this thinking LiteLLM would do the routing, and it doesn't, it logs. The proxy sits between Claude Code and Anthropic, passes your normal login straight through, and writes down every request by model, which is what you need to see where your volume goes and nothing more. Run it in Docker with Postgres behind it and start it with one `make` command. "Why isn't Claude Code using it?" Because on WSL the VS Code setting holding the proxy URL is machine-scoped and has to live in `~/.vscode-server/data/Machine/settings.json`, not your Windows User settings, and nothing warns you when it's in the wrong place.

One more thing about it. My chats sometimes hung when Anthropic's usage limit was reached, as if the limit message never came through. I couldn't reproduce that; the proxy passed Anthropic's rate-limit errors back to the client in its logs, and a direct call and a proxied call behaved identically when no limit was hit. I still took the two proxy variables out of my editor settings, so chat talks to Anthropic directly and only the benchmark runs go through the proxy, because a logging convenience isn't worth a chat that hangs.

## Automatic routers pick the wrong jobs

LiteLLM ships routers that score each prompt and choose a model, which sounds like the obvious next step, so I tested two on a set of tasks I had labelled by hand. The keyword router sent all five of my cheap prompts to the cheap tier and none of the three hard ones to the top tier, because "review this authentication flow for security vulnerabilities" is plainly worded and a keyword scorer can't tell it's hard. The capability classifier, with a small free model as the judge, got six of ten decisions wrong or fell back to the top tier. A stronger judge would do better, but then every request pays for a strong-model call before any work happens, which undoes the saving, and I didn't test that. I also dropped the free hosted model for tool-using agents, since an agent that reads a file, edits it and checks the result eats an eight-thousand-tokens-a-minute limit fast.

## The orchestrator

The idea was one central agent that decides when a job is big enough to delegate and when it needs review, using a fixed table so the line is drawn the same way every time. It estimates a handful of signals (files, lines, modules, ambiguity, risk, novelty, whether there's a spec, how many edge cases are listed), a small script turns them into a delegation level and a review level, and it has to write the answer on its first line before it does anything.

To test whether it draws the line consistently I gave it twelve task descriptions three times each. Early on it added the scores up wrong in roughly four replies out of ten, so I made it call the scorer instead of doing the sum, and the scorer was being refused. In headless mode a Bash call needs a permission rule, I hadn't written one, so the model said it couldn't run the tool and estimated by hand, or skipped the line entirely. Once I allowed that one command, the arithmetic was right in all 36 replies and the same action came back on 35 of 36 repeats. Thus the "model can't add" problem I'd been tuning prompts for was a permissions problem, which is the sort of thing you only find by reading the raw replies.

## What I measured

I ran three conditions on each task: plain Sonnet, plain Sonnet told to review and fix its own work once before finishing, and the orchestrator. Here's the one scenario where they diverged a little, a library back-office feature with ten requirements and a trap where charging a fee can be refused, three runs each.

| Condition | Scores | Mean cost | Mean time |
| --- | --- | --- | --- |
| Plain Sonnet | 0.88, 1.0, 1.0 | $0.82 | 4 min |
| Plain Sonnet, one self-review | 1.0, 1.0, 1.0 | $0.78 | 5 min |
| Orchestrator | 1.0, 1.0, 1.0 | $2.83 | 16 min |

The one low score was real, plain Sonnet ignored the error from the balance update and returned a receipt for a fee that was never charged, and it didn't mention the case in its report. Both other conditions got it right in all three runs. The orchestrator cost about three and a half times what the self-review did, for the same score. The orchestrator also broke its own rule of six delegations in one run, used eight, and finished 37 seconds before my runner's timeout.

"Isn't that a win for review?" Possibly, but it's one miss in three runs, so I wouldn't bet on it.

## When every score is 1.0

If every condition scores perfectly, the test can't show a difference, whatever the truth is. Think of a tutor and an exam so easy that everyone gets full marks, you'd learn nothing about the tutor. That is what kept happening to me, plain Sonnet scored at or near the ceiling on a recurrence-rule library, a CSV importer with five review comments (one of them deliberately wrong, which it correctly refused to act on, three times out of three), and the library feature above. The orchestrator can only tie a perfect score.

That is a statement about my tasks and not about the orchestrator. Every prompt I wrote was precise and self-contained, and the problems I actually hit in daily work come from loose requests, an existing repo with its own habits, and requirements that move, none of which these tasks recreate. Repo conventions, work that gets lazy halfway, and front-end work are the three I care about most, and the benchmark never exercised them, so I can't say anything about them.

## A harder scenario, and seven ways of improving on plain Sonnet

Since every earlier test saturated, I built one that wouldn't: a roughly twenty-file helpdesk back end and a sixteen-requirement ticket written the way a real one is, with an escalation reason that has to stay hidden from customers in five different places a ticket is shown, two of which are reached only through older code, plus quiet-hours and clock-pause rules the ticket doesn't define. Plain Sonnet averaged 0.92 over three runs (0.86 to 0.97), at about $2.50 and eleven minutes a run, so there was finally something to improve on, about a tenth.

I tried seven ways of improving it, each three runs, each judged against a margin I fixed before running anything (a mean at least 0.05 higher, with two of three runs above plain Sonnet's mean).

| Method | Mean | Runs | Mean cost |
| --- | --- | --- | --- |
| Plain Sonnet | 0.92 | 0.94, 0.97, 0.86 | $2.50 |
| Build, one fresh reviewer, then a fix pass | 0.93 | 0.82, 0.98, 0.97 | $3.46 |
| The same, with the reviewer limited to the changed files | 0.87 | 0.98, 0.76, 0.86 | $3.04 |
| A work graph the agent fills in and must clear | 0.91 | 0.86, 0.88, 0.98 | $2.63 |
| One self-review pass | 0.86 | 0.88, 0.85, 0.86 | $2.30 |
| A flat checklist file | about 0.80 | 0.54, 0.88, 0.75 | $2.33 |
| Code-graph tools offered, never used | 0.83 | 0.86, 0.77, 0.87 | $1.75 to $2.07 |
| Serena's reference search required for every symbol changed | 0.82 | 0.73, 0.87, 0.87 | $2.67 |

None of them cleared the margin, and the spread between single runs, 0.75 to 0.98, was bigger than any gap between the means. The checklist's first run was dragged down by a bug in my own scorer, so treat its 0.80 as rough.

"But you said a graph was the next step?" It was my hunch, and this tests one small form of it, so it doesn't settle the question. The graph was a script that records requirements, the changes that implement them, the tests that verify them and any problems noticed, with one command listing what's still unverified that the agent must clear before finishing. The agents used it properly, eight to thirteen calls each, around twenty requirements, changes and tests recorded, but none of them recorded a single problem, so it worked as bookkeeping and never made the agent notice something new. What the runs missed was edge-case judgement, an override with a whitespace-only reason went through in every run I checked, and a requirement graph is built to catch forgotten requirements, which weren't the problem here.

The reviewer variant looked like the one to watch. Two of its runs scored among the highest I recorded (0.98 and 0.97) and one among the lowest (0.82), the reviews were real, but the fix pass acted on every serious finding including a stale holiday list in code the task never touched, which is churn you didn't ask for, and it cost between 90 cents and $1.20 here against 3 to 15 cents on the smaller task I'd first tried it on. So I limited it, the reviewer got the list of files the task had changed and was told to report on those only, and the fix pass was told to leave everything else alone. The churn went away and the fix pass dropped to between 30 and 50 cents, but the mean dropped too, to 0.87 against 0.93, with one run at 0.98 and one at 0.76. Scoping the reviewer isn't the missing piece, and three runs won't let me claim more than that.

The last two were the code-graph tools, servers that index a repo and answer "who uses this?" without grepping. Offered to plain Sonnet with a paragraph telling it to use them, they got no calls in three runs out of three, the servers connected, the tools were listed, and it carried on with Grep, Read and Edit, so that 0.83 is plain Sonnet plus a paragraph and the test was void. So I forced it, and found the first problem before spending anything: one of the servers, the cheap index, answered "not found" for a function with three callers, because this repo calls everything as `visibility.redact(...)` and the index doesn't see calls written that way, while Serena's reference search found every caller. Requiring Serena for every symbol changed got 10 to 14 calls a run, correct answers, and a mean of 0.82 against 0.92 for plain Sonnet. Most of that gap is my instruction, which asked for a list of the symbols checked in the final message and pushed out the statement of the choices the ticket left open, so that part of the score went to zero in all three runs, and without it the forced runs land at about 0.91. The tool had nothing to find, the legacy surfaces were never where plain Sonnet failed, so on a twenty-file repo it didn't help, and a repo too big to grep is still untested.

## Carrying rules from one session to the next

A work graph that lives inside one session can only ever be bookkeeping, and what I actually wanted to know is whether state carried between sessions helps when the second session has no memory of the first. That's closer to how I work, Monday's ticket sets a rule, Thursday's ticket touches it, and Thursday's session has never heard of Monday.

So I chained two tickets on the same repo. The first adds ticket merging and ends with three rules in plain words: a merged duplicate is never counted anywhere tickets are counted, the list of what was merged in and the escalation reason are for staff only, and the customer who filed a duplicate still sees it and where it went. The second, done in a fresh session on whatever the first left behind, asks for a weekly digest for team leads and a weekly status email for customers, and says only "the usual rules apply". Hidden tests check whether the rules turn up on the new surfaces. I ran plain Sonnet six times and every carrier three times, except the work graph, which I ran six times because it kept coming close.

| Condition | Score | Carried rules | Mean cost | Mean time |
| --- | --- | --- | --- | --- |
| Plain Sonnet | 0.89 | 0.67 | $2.12 | 9 min |
| NOTES.md the agent keeps | 0.89 | 0.67 | $2.24 | 12 min |
| Rules as tests, written by the agent | 0.87 | 0.67 | $2.70 | 14 min |
| CLAUDE.md written by the agent | 0.86 | 0.67 | $2.06 | 11 min |
| Work graph the agent keeps | 0.93 | 0.78 | $2.90 | 13 min |
| CLAUDE.md written by me from the ticket | 0.99 | 0.96 | $2.19 | 10 min |
| Rules pasted into the second ticket | 0.99 | 0.96 | $2.19 | 12 min |

"Carried rules" is the part of the score for the three rules on the new surfaces, and I fixed the bar before any run: a mean at least 0.05 above plain Sonnet, most runs above plain Sonnet's mean, and the carried-rules score at least 0.10 higher. Only the CLAUDE.md I wrote myself cleared it, and it matched the pasted-rules ceiling exactly at 3 per cent more money. The graph came closest of the rest, a consistent 0.04 ahead on score and 0.11 on carried rules over six runs against six, but it missed the score bar by 0.01 at more than a third more money and nearly half as long again, so I'm not counting it.

What decided it was who wrote the carrier, not where it lived. The agent's notes file, its rule tests and its own CLAUDE.md all scored the same 0.67 on carried rules, and the reason is sitting in the files: the first session wrote all three rules down faithfully, and then wrote down its own reading of the third, that a merged duplicate is hidden from every list and reachable only by looking it up directly, which isn't what the ticket said. In the rule-tests run the second session went further and added a test saying only the primary is listed in the customer's status, so the wrong reading was enforced on the new surface. The same file under the name CLAUDE.md, which Claude Code loads without being asked, changed nothing, so the problem wasn't that the agent skipped reading it.

That makes anything the agent writes for itself a place where your mistakes get carried as faithfully as your rules. Once the first ticket is done, copy the rules into CLAUDE.md yourself, it took the carried-rules score from 0.67 to 0.96 and cost me one paragraph, or say them again in the ticket that needs them. The caveats are that my rules were correct by construction, that the human step is part of what I'm recommending, that the first session still dropped the duplicate from the customer's list in every run because the file only arrives afterwards, and that three runs per cell can only show a big effect.

## The model changed while I was measuring

On the last day, a batch of three runs went through with the first one costing $2.92 and the next two costing 65 and 45 cents. I read the model on each run before reading its score, as I'd learned to, and the last two said `claude-sonnet-5-5` where every run in the project before them said `claude-sonnet-5`. Claude Code had updated itself between the first and second run, and from then on the name "sonnet" meant a different model. I moved the two runs out of the results, pinned the model by its full name in the runner, and checked that the pin holds, though I can't pin the Claude Code version, which went from 2.1.266 to 2.1.309 and is a small confound I'm naming and not fixing. If you've written `model: sonnet` in your agent files, as I did, your agents moved at the same moment.

So I ran plain Sonnet on the new model, three runs on each scenario. On the helpdesk task it scored 0.96 against 0.92, at 44 cents against $2.50 and about two minutes against eleven, which is 18 per cent of the cost and 21 per cent of the time. On the two-ticket chain it scored 0.97 with carried rules at 0.89, against 0.67 on the old model, and the one thing it missed every time was the pointer from the merged duplicate to where it went. The CLAUDE.md I wrote fixed that in all three runs, 1.00 on both numbers, for about 15 per cent more money. The advice carries over and matters less, because there's less left to fix.

That's also the catch. Both scenarios are now close to the ceiling for the newer model, 0.96 and 0.97, so any process I add can win by about 0.03 and no more, which is the "every score is 1.0" problem again, so I stopped scoring out of 1 and built something that counts, in the next section. Everything above that compares methods is a finding about the model I started with.

## Counting what a reviewer would flag

A mark out of 1 isn't the number that costs me time. My team gives about one review a day between us, so a pull request that sits in review for one or two days and not three to five is worth a lot, and what decides it is how many comments come back, which is about ten on a typical PR of mine, where two would be great. So I built a scenario that counts comments instead of marks.

It's four small TypeScript repos side by side, a service, a billing service, a backend-for-frontend and a web app, and three tickets in fresh sessions, one per repo, with the last one saying only "use the endpoint from the previous ticket", which is how mine read. The agent can open the neighbouring repos, and nobody tells it to. The first ticket changes the shape of an order's total, which the other three repos read. There's a real bug in the code it has to touch, next to a duplicated function that's tempting to tidy, the second ticket names a field the code calls something else, the third asks for a delivery date nothing provides, and one docstring goes false when the total changes. Scripts count a flag for each thing a reviewer would raise: a consumer left broken, an edit outside the ticket that the report doesn't mention, a stale docstring, a repo pattern missed, a test bent back to the old behaviour. Plain Sonnet averaged 8 flags a job over six runs, between 7 and 9, which is close enough to my ten.

It took three passes to get there. The first came out at 10 flags in all three runs, and the cause was mine, since the prompt never said nobody could answer, so in the last ticket the agent wrote no code and asked me which of three options I wanted. One line saying the session is non-interactive fixed that, and the next three runs scored 5, 6 and 5, which was too easy by the bar I'd set (7 to 14), so I added four traps, once, as the rule said I could, and plain Sonnet landed on 9, 9 and 8. Before any of that, a fresh reviewer I pointed at my own checker found four faults in it. It flagged 8 of 11 honest ways of saying the delivery date wasn't available, it counted the TODO file my checklist condition tells the agent to keep as an out-of-scope edit, it excused an agent that had changed the planted bug whenever the report happened to mention the function, and it flagged helpers that any reviewer would let through.

The bar was fixed before any run: a method works if it averages a fifth of plain Sonnet's flags or fewer (so 1 or less), most runs beat plain Sonnet, and it stays inside my cost lines, up to twice the cost if it removes at least 3 flags and up to four times if it removes at least 6. Three runs each to start with, six for the four I came back to, same model, same checker.

| Method | Flags per job | Mean cost | Mean time |
| --- | --- | --- | --- |
| Plain Sonnet (six runs) | 9, 9, 8, 7, 8, 9 | 34 cents | 98 s |
| Rules file I wrote | 2, 2, 3, 3, 3, 6 | 38 cents | 112 s |
| The same rules minus the one about checking every caller | 7, 8, 6, 8, 7, 8 | 37 cents | about 2 min, one run hung for 14 min |
| Rules a fresh agent wrote from my list of complaints | 6, 9, 6 | 40 cents | 104 s |
| Rules, checklist and reviewer together | 2, 5, 2 | 75 cents | 241 s |
| Reviewer told to check every consumer | 3, 13, 3, 13, 4, 3 | 75 cents | 247 s |
| The same, with the fix pass allowed to edit other repos only as far as consumers need | 3, 3, 2, 3, 4, 3 | 69 cents | 219 s |
| Reviewer reading the changed files | 9, 8, 7 | 62 cents | 200 s |
| Orchestrator | 10, 9, 7 | 38 cents | 148 s |
| Flat checklist | 10, 9, 9 | 39 cents | 100 s |

Nothing cleared the bar, and the rules file and the limited fix pass came closest, a 62 and a 64 per cent cut. The rows with the caller rule removed, the rules a fresh agent wrote and the limited fix pass, and the extra runs behind them, are follow-ups I added once I'd seen the first results, so they weren't part of the plan I fixed in advance.

- **Plain Sonnet.** Most of its 8 flags are one failure. It changes the shape of the total, says in its report that this will break anything reading it, and never opens the billing service or the backend-for-frontend that do, so five or six of the flags are consumers it left broken and didn't name. It also fixes the planted bug without being asked, which is the sort of edit outside the ticket that draws a comment.
- **The rules file.** I wrote the rules from my own list of review comments, check the callers of anything shared, raise out-of-scope problems and don't fix them, update tests and don't bend the code to an old one, and over six runs it updated the consumers in five. "Isn't that cheating, you wrote them with the checks open?" Partly, so I ran it again with a single bullet removed, the one that says to check every caller in all the repos before changing a shared endpoint. The consumer flags went straight back to plain Sonnet's level, five or six in every one of six runs, and the total to 7 against plain Sonnet's 8, so nearly all of the cut came from that one rule and the other eight together took off a flag or two. Then I gave a fresh agent only the list of review complaints I'd worked from, with no sight of the repos or my checks, and had it write the rules. Its version had a caller rule too, find every caller and importer, state who is affected, confirm each one still works, plus the tests, typing, comments and scope rules, and it got 6, 9 and 6 flags, with the consumers left broken in all three runs. In the first ticket it made five tool calls and none looked outside its own repo, since a rule to check callers reads as this repo unless it says otherwise. So in that scenario a rules file worked when it named the exact repos that consume a shared contract, and a general list of good habits did very little, although the second scenario below says the general list does a bit more than that.
- **The reviewer.** The one I'd tested before looked at the files the job changed, in its own repo, and never saw the consumers, so the flags barely moved. Told that the four repos sit side by side and to read every consumer of anything changed, it found them and the fix pass updated them, with zero consumer flags in all six runs. In two of those six the fix pass, which I'd let edit the other repos, changed nine files across them, and in the first it invented delivery dates for seven orders, so those two runs scored 13 and the other four scored 3 or 4. That is a decision about what the fix pass may touch, not a verdict on reviewing, and when I told it to edit other repos only as far as keeping the consumers working, with no new fields, endpoints or data, six runs scored between 2 and 4 with no consumer flags and no overreach. It also still left the planted bug and the duplicated function alone without raising them, which is what the rules file does better, and at 69 cents against 38 it costs nearly twice as much. Its edge is that it fixed the consumers in six runs out of six, where my rules file managed five.
- **The checklist and the orchestrator.** A checklist only makes the agent list its own tasks, so the flags came out the same as plain. The orchestrator did the work itself in most sessions and called a reviewer in some, which didn't make it open the consumers either. These tickets are small, and I haven't tested a job big enough to make it plan and split.

All of that rests on one task I wrote, so I built a second in a different domain, clinic bookings, with a bookings service, a notifications service, a backend-for-frontend and a web app. A slot's start time changes from "09:00" to a full timestamp, one consumer reads it through its own adapter so searching for the endpoint finds nothing, and the same kinds of planted bug, tempting refactor, mismatched field name and missing data sit in the way. I wrote down what would count as a replication before any run, copied the rules files across without changing a word, and plain Sonnet landed on 10.7 flags over six runs, a little above the first scenario's 8.

| Method | Flags per job | Mean cost |
| --- | --- | --- |
| Plain Sonnet (six runs) | 11, 10, 10, 11, 11, 11 | 50 cents |
| Rules file I wrote | 4, 4, 4 | 47 cents |
| Rules a fresh agent wrote | 9, 5, 9 | 53 cents |
| Reviewer told to check every consumer, fix pass limited | 6, 6, 5 | $1.00 |
| Rules, checklist and reviewer together | 3, 6, 4 | $1.06 |

The rules file held up, a 62 per cent cut with every run below plain Sonnet, but not in the same way. Here the agent named the broken consumers in its report and left them broken ("outside this ticket"), left the planted bug alone and said so, and stopped editing the backend-for-frontend from the web ticket, which plain Sonnet did in every run, four files each time. So the review burden fell and the consumers were still broken when the pull request landed. The reviewer did the reverse, repairing the consumers in all three runs and still letting the front-end session edit the other repo, and putting them together didn't add up, since rules, checklist and reviewer came out at 3, 6 and 4, no better than the rules alone for twice the money. The rules a fresh agent wrote cut 28 per cent, which my pre-written line counted as neither a replication nor a failure. The stack's recorded numbers include two flags my checker raised for a next free time it called made up, although the agent had worked it out from real data, so by hand they'd be 3, 5 and 3. I kept the recorded numbers because I'd frozen the checks, and I'd already had to fix a false flag of that kind during calibration.

The caveats are the usual ones and they matter here. Three to six runs per method means only a big effect shows, nothing is blind, and both tasks were designed by me, so they say what these methods do on a repo of four small services and not on yours, and the second one shows the first wasn't an accident of orders and billing, no more than that. I wrote the main rules file with the checks in front of me, and the rules a fresh agent wrote are the nearest I got to a blind version, although they came from the same list of complaints and not from anyone's real review history, which I didn't have to hand. One of the follow-up runs hung on a background command and my runner scored a stray cleanup message as the ticket report, which added two false flags; I re-scored it by hand, the table shows the number the runner recorded, and I changed the runner so it can't happen again. The runs cost about $46 on top of the builds, one of which I can't price because my machine froze while it ran, and $6 of that went on a first attempt at the second scenario that I had to throw away (see below).

## Bigger jobs, longer chains and two other languages

Those results left three holes I'd named myself, so I filled them, on the same model with its full name pinned and read on every run, and the same flag counts and bars I'd written down before running anything.

The first hole was the orchestrator on a job big enough to split, which is the only place it could earn its cost. I built a front-end job for it, a component library with 24 components and nine new colour themes for each, 216 files, where a theme counts as done only if it renders, is registered, isn't a placeholder, and differs from the default in structure and not just in class names. What I was waiting to see is what I see on real work, an agent doing the first few components properly and then copying the default into the last third. At a first, small size the plain run finished everything, so I rebuilt it with themes the size real ones are, 90 to 140 lines each, and the first run at that size looked exactly like decay, 161 cells of 216 done and the last third at 25 per cent. I nearly wrote it up. Then I read the agent's own report, which said it had run out of budget, and the cause was a $5 cap per session that I'd hard-coded into my runner and forgotten, so what I'd measured was my own limit. With the cap at $25, three plain runs finished 215, 216 and 216 cells, the thirds came out flat, and the job cost between $5 and $6 and about 25 minutes when the agent worked alone, or 7 minutes in the one run where it decided to hand the work to 12 workers itself. Plain Sonnet doesn't decay on this job, and I can't tell you why it does on mine.

The orchestrator finished 216 of 216 in both of the runs that count, with 13 and 11 flags against plain's 10 to 12, at $6.38 and $6.72 against $5.42 for plain on average, so about 1.2 times the cost for the same result. It was faster than plain working alone, 15 and 19 minutes against 25, but not faster than the plain run that delegated for itself, so the speed comes from parallel workers and plain can start those without being told to. A third orchestrator run died on a rate-limit error from the proxy on its last call, with no final report, and had sent part of the work to an Opus agent for $2 of its $8, so I left it out and say so here. One pattern, which at this size is an observation and nothing more: every run that delegated and left a report missed the same three things in it, the gallery, the default themes and a token mismatch, where the two runs working alone named them.

The second hole was the long stretch. I added two tickets to the clinic chain, so five in a row, and the fourth goes back to the contract the first one built, renaming `remaining` to `free` and hiding full slots from the list unless you ask for them, so the consumers the agent itself wrote in tickets two and three break unless it finds them. I added a count for exactly that, earlier work that passed after the third ticket and fails after the fourth or the fifth.

| Plain Sonnet (six runs) | 15, 17, 15, 16, 15, 18 | 3 in every run | 76 cents |

Plain Sonnet broke the same three pieces of its own earlier work in all six runs, the backend-for-frontend's availability route, the day-of reminders and the booking page, and its report never named them. The rules file cut the total by a third, and the cut thinned as the chain went on, since in tickets four and five together it left 3.7 flags against plain's 5.3, and only one of its three runs repaired the consumers. The reviewer cut the total by more than half and repaired the consumers in all three, at about twice the cost. By the bar I'd fixed, neither works and the reviewer is partial, but the shape is the useful part, because over three tickets a rules file looked like most of the answer and over five it looked like the cheap half of it.

The third hole was that all of it was TypeScript. I ported the clinic chain to Go and to Python, same four repos, same traps, same tickets apart from one line that names a function, the same rules file with only the language words changed (one line in Python, two in Go), and checks of my own for each, which turned out to be the hard part. My first Go gate runs all carried one flag for a test with no "Then", where the agent had written the title as two strings joined together and my check read only the first. In another, my notes said Go 1.26 and Python 3.14 were installed, and the shell I was running in used Go 1.24 and a Python 3.11 from a virtual environment, so I pinned both in the runner and have it write the version into every result.

The TypeScript result carried over to both. The rules file cut the count by 64 per cent in Go and 69 in Python, the reviewer by 58 and 69, every run below plain Sonnet's mean, and my rule for "it holds in this language" was met in both. What didn't carry over is the price of the reviewer, which was 1.8 times plain in Python and 5.2 times in Go, and I haven't worked out why. It was also uneven in Python, one run at 1 flag and two at 5, because in two of them the front-end session still edited the other repo. The rules file cost no more than ten cents above plain in both, so on this evidence it's the one to try first, and the reviewer is the one to pay for when you can afford twice the bill or more.

## Reviewers are the cheap win

I then tested the review step on its own, handing a reviewer code with known defects and counting what it found. Three reviewers (the project's Sonnet reviewer agent, the same agent on Opus, and plain Sonnet with a generic prompt) read three codebases, 15 runs in all. Every one caught every known serious bug, including a real one a Sonnet agent had written, where a refused fee was silently dropped. The Sonnet reviewer agent was also the cheapest and fastest, between 13 and 23 cents and about one to two minutes a run, plain Sonnet cost roughly one and a half to two and a half times that, and Opus roughly two to four times, with more findings that were harder to trust (one claim, that the README's test command fails, didn't reproduce when I ran it).

Two things in there surprised me. In the code I had labelled clean, all six reviewers found the same genuine bug, the loans report ignored the staff exemption, so the reference solution I'd verified with my own tests wasn't clean at all. And twice, a reviewer hit its turn cap and returned nothing: I'd told it to write its report by its eighth tool call, but calls run in parallel batches, so fourteen turns held about thirty calls. Count turns, not calls, tell it to batch its reads in the first turn, and give it room.

So finding the bug isn't where the process fails. A fresh Sonnet reviewer finds it for about 20 cents and a minute or two, and whether it happens at all is up to whoever decides to call it, which is exactly the thing the orchestrator was supposed to improve and didn't do reliably.

I reran all of this on the newer model with the model pinned by full name and checked on every run, 24 runs across four codebases for $3.46. Every reviewer again caught every serious bug it was handed, although my keyword scorer marked two of them as misses and reading the reports showed both had caught it, so I scored those by hand. The Sonnet reviewer agent cost 7 cents and half a minute a run, plain Sonnet 12 cents, and Opus 25 cents for no extra catches. The extra findings on the two codebases I'd labelled clean needed a closer look, so I had the Serious ones judged against the code with working reproductions, 29 items that came to 15 distinct findings. Five were real, nine were true but intended, trivial or out of scope, and one was wrong, and about 45 per cent of each reviewer's Serious findings were clearly real, Opus included, so its extra cost bought no extra accuracy. Two things came out of it. Both "clean" codebases contained real defects my own tests never covered, one of them a customer-visible leak in the helpdesk, where `set_status` hands the customer the escalation reason and the internal notes. And the Sonnet reviewer agent and Opus both missed that leak in every one of their four helpdesk reports where plain Sonnet found it in both of its two, which is two reports per cell and so a warning and not a ranking. Catching every seeded bug is true, catching every real one in a twenty-file repo is not.

## My measurements kept lying

If you build a benchmark, plan on this, because every time I trusted a result I hadn't read, I was wrong. The Opus judge scored the orchestrator low three times for reasons that were mine: it truncated files at 6,000 characters, so long test files looked cut off, it scored files that agents had correctly written outside the project, and it only saw files the model had written, not edited, so it gave a false 2 out of 5 for "missing" files. The orchestrator's first score on the library scenario was 0.72 because my function finder rejected its perfectly good signature; on the harder version the finder picked a helper that returned a day count; and one self-review run lost points because I handed the wrong date to a parameter called `returned_on`. I fixed each one, scored again, and wrote a test that proved the fix by failing without it, which is how I found my first attempt at one of those tests passed with the bug still in place.

Two more of mine, from the harder scenario. Two runs stopped by my weekly usage limit lasted two seconds each, cost nothing, and my runner scored them as 0.3 because it only recognised the word "session", so look at cost and duration before you look at a score. And my reviewer condition was scored on the last message alone, the fix pass's summary, which never repeated the choices the build made, so it lost a tenth of its score for how it reported, not for what it built; I re-scored it from a saved copy of the project, and my runner now saves one for every run.

Four more came from the middle stretch. Two turned up in the scoped-reviewer batch: my check didn't recognise `quiet_hours` with an underscore, so two runs that had stated their choice scored nothing for it, and I docked the scope score when an agent removed a TODO comment by doing the work the comment described. In the two-ticket test my export checks failed every run, plain Sonnet included, because they wanted the customer's CSV to have no merged-from column at all, and all nine runs I'd made by then had kept the column with blank cells for customers and leaked nothing, which hides the data and is what the ticket asked for, so I'd tested the layout of my own reference and not the rule. And a scorer that wanted a new call to the "active tickets" helper marked down all three plain runs that had done the right thing by changing the helper itself.

The fresh reviewer I pointed at my own reference solution found a real bug in it too, a customer whose only ticket had been merged away never got the weekly email, and plain Sonnet made the same mistake in all three runs, so my tests had been blessing a mistake the model also makes. Later a run gave the user model a flag of its own to say who leads a team, which the ticket never defined, and my tests only knew "an admin on the team", so three tests failed a design the ticket allowed. I fixed each one with a test that fails without the fix and re-scored every run from the saved copy of its project, and the numbers moved together, but I changed them after seeing them, so none of this is blind.

Two more from the last stretch. The run that looked like the agent giving up on the last third of a 216-file job was my own $5 budget cap, which I only saw because I read the agent's report before the score, so a cost limit can pass for decay, and a rate-limit error from the proxy can pass for a bad run in the same way. And the Go check had a first draft that flagged correct work, a test title built from two strings that it read half of, so every plain run drew a flag it hadn't earned until I looked at which test it pointed at.

Worth knowing, too, if you run agents headless. A usage limit stops a run halfway and leaves junk unless your runner exits without recording it, a loop that silently rejects every argument still prints "completed", and a background wait ceiling of 600 seconds will cut an orchestrator off while its reviewer is still working. A "completed" notice from a background job isn't the job finishing either: three times a batch had stopped while the notice said completed, once for a reason I never found, once on a usage limit and once because my session ended, and one run was left with empty result files because the session died while it was writing them, so check the result files and not the notice. Once an agent left a hung background command behind and Claude Code ran a stray extra turn about it, which put a reply about the notification where my runner expected the ticket's report. Check the first line of output before you trust a finish message. And pin the model on every batch, because my runner defaults to an older Sonnet, I started the second scenario's first three runs without setting it, and I only found out from the model counts in the result files, after spending $6 on numbers I couldn't use.

## What I'd do, and what's next

Pin models and effort in the agent files, and pin them by full name if you want the same model next month, because the aliases move when Claude Code updates and everything built on them moves with it. Add one fresh Sonnet reviewer pass for anything that touches money, data or a public interface, tell it which repos sit next to the one it's reading and to find every consumer of anything that changed, because a reviewer only sees what you point it at, and tell the builder to fix only the serious findings inside the ticket and say so if it disagrees, because a fix pass allowed to edit other repos will do exactly that. Skip the orchestrator unless your own tasks are loose and large enough that planning and splitting would earn their cost, and test that on your own work first, since on my three-ticket jobs it mostly did the work itself and on a 216-file job it cost about 1.2 times plain Sonnet for the same result, where plain Sonnet could start its own parallel workers when it chose to.

If a rule has to survive from one session to the next, write it into CLAUDE.md yourself or say it again in the ticket that needs it, and don't ask the agent to keep notes, tests or a graph of its own rules, because those carry a wrong reading as faithfully as a right one. The same goes for the comments your reviewers keep repeating, write each one down as its own concrete rule that names the repos and files involved, since that took my count from about eight to about three, with nearly all of it coming from the one rule that named the biggest problem and the repos it lived in, and from about eleven to about four in the second scenario, and in Go and Python it did the same. Over five tickets in a row the rules file's effect thinned and the agent still broke its own earlier work in two runs of three, so for a long stretch the reviewer that goes and reads the consumers is the part worth paying for. Read what the next session was handed before you trust it.

What I haven't done is the part that hurts most day to day. I've run five tickets in a row, the orchestrator on a job big enough to make it delegate, a front-end job and two other languages, but every one of those is a task I wrote, checked by scripts I wrote, with traps I put there, so they show what these methods do on my stand-ins and not on your repos, and I haven't tried the code-graph tools on a repo big enough to need them. My stand-in tickets are also far smaller than the ones that draw my ten comments, and the decay I see on real jobs is one thing I couldn't make happen on purpose. None of it is cheap to test either, building the two-ticket scenario cost nearly $19 with the orchestrator doing the build, and before I'd trusted either scenario a fresh reviewer had found faults in my own reference solution or my own checker.

Give it a week, look at the split, and move one job down a tier. Good luck, and if your numbers come out different to mine, I'd like to hear about it.
